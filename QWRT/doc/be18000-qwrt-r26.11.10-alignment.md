## Key divergences and risks

1. **Memory profile is not the live unit's map.** The new DTB carries a root
   `MP_512;` property and `qcom,tgt-mem-mode = <1>`, with smaller/moved
   QCN9224 windows:
   - QWRT: pcie0 0x4cf00000, pcie1 0x4f400000, pcie2 0x51900000,
     pcie3 0x53e00000, each 0x2500000; hremote 0x1400000, pageable
     0x700000; wcss 0x1d00000.
   - Live/mainline: pcie1 0x50f00000, pcie2 0x54100000,
     pcie3 0x57300000, each 0x3200000; hremote 0x1c00000, pageable
     0xc00000; wcss 0x2b00000.

   The live unit reports 1,833,244 kB RAM and its DTB does **not** carry
   `MP_512` or `tgt-mem-mode=1`.  The new map is a different hardware or
   firmware memory profile.  Do not merge it into our DTS without
   confirming what `MP_512` selects.  In particular, the new
   `qcn9224_pcie0@4cf00000` window overlaps our `ramoops@4dd00000`.

2. **MLO is enabled by default in QWRT.** The new image uses
   `cnss2.enable_mlo_support=1`, the QSDK `wsi` node and
   `mlo_global_mem_0`.  Our implementation deliberately keeps MLO opt-in
   and uses the mainline WSI endpoint graph.  Do not enable MLO based on
   this image alone.

3. **Firmware/BDF delivery differs.** QWRT ships QSDK `amss.bin`, `m3.bin`
   and `bdwlan.b0001/2/4` (63,488/100,352/100,352 bytes).  Our mainline
   uses `ath12k-firmware-qcn9274` plus the live unit's 292,256-byte
   `board-2.bin` (`0fcbb66e...`).  The new QWRT `bdwlan` files have the
   same sizes as the live ART BDF slices but different hashes.  They are
   generic vendor BDFs, not the live per-unit ART calibration; do not
   replace the live `board-2.bin` with them without a separate analysis.

4. **SFP is a LAN port in QWRT.** QWRT `02_network` uses `eth0 eth1 eth2
   eth3 eth5` as LAN and `eth4` as WAN, i.e. the SFP PHY at 0x1e is part
   of LAN.  Our mainline leaves `port@6` disabled until a mainline SFP
   driver is validated.  This is intentional.

5. **The vendor `fw_env` path is still wrong for be18000.** QWRT's
   `30_uboot-envtools` handles be10000 with 0x10000/2 sectors but lets
   be18000 fall through to the generic 0x40000/2-sector calculation.
   The live be18000 environment CRC validates over the first 64 KiB only,
   so our `/dev/mtd17 0x0 0x10000 0x20000 1` remains correct.

## Verdict

The mainline implementation is aligned with the vendor image on the
important **board topology and boot contract**:

- three-volume UBI layout with autoresizing `rootfs_data`;
- `config@al02-c4`, gzip, `0x42080000`;
- the same PCIe controller addresses and lane widths;
- the same AQR113C/QCA8084/SFP MDIO addresses;
- the same four-copper-LAN plus AQR-WAN role split and ART MAC offsets;
- the same LM63/EMC2301 thermal/fan devices and LED/button labels.

It intentionally differs on the **QSDK-specific layers**: memory profile
(`MP_512`/`tgt-mem-mode=1`), default MLO, QSDK WSI, QSDK firmware/BDF
delivery and the SFP LAN role.  Those should not be copied into the
mainline port without hardware evidence.

The immediate conclusion is: **no mainline DTS change is justified by
this image.**  Keep the live unit's reserved-memory map, keep the live
`board-2.bin`, keep MLO opt-in, and keep SFP disabled.  The next useful
checks are to identify what `MP_512` selects and to compare the new QWRT
BDFs against the live ART-derived BDFs, but only as separate experiments.

## Working-tree note

At the time of this check, the repository also contained uncommitted
changes that were not part of the built images in `build/`:

- a 1 GiB `memory@40000000` node;
- `rsvd1@67300000` / `rsvd2@67340000` reservations;
- an optional `BE18000_TESTING` package hook and `testing/` scripts;
- updated FIT/U-Boot analysis documents.

The `rsvd1`/`rsvd2` ranges match the QWRT board DTB.  The QWRT DTB does
**not** contain a `memory@` node; its bootloader supplies RAM.  The
working-tree 1 GiB node is therefore not a QWRT-derived fact and remains
unverified.  These changes are not in `build/`; rebuild before flashing
if they are intended to be part of the candidate.
